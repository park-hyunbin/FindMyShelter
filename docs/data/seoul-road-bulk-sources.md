# 서울 전역의 차선·차도 일괄 수집

2026-11-22에 공개 파일을 내려받아 서울 25개 구의 차선과 차도 도형을 비교했다. 서울시 원본을 레이어별로 한 번씩 확보한 뒤, 도시 단위 공간 인덱스에서 단지나 생활권에 필요한 부분을 꺼내 쓰는 방식이다.

표에 있는 서울시 선·면 자료의 좌표계는 EPSG:5186이다. 전국 표준노드링크는 ZIP의 원본 좌표계를 읽어 EPSG:5186으로 변환한다. 파일 날짜는 원본 관측일을 보장하지 않으므로 출처, 파일 버전, 관측일과 좌표계를 각각 기록한다. [서울시 차선 자료](https://data.seoul.go.kr/dataList/OA-15537/S/1/datasetView.do) · [에스맵 오픈랩](https://openlab.eseoul.go.kr/) · [2026년 버스전용차로 자료](https://data.seoul.go.kr/dataList/OA-22396/F/1/datasetView.do)

관리번호가 일치한 버스전용차로 중 두 시점의 선형 거리를 계산할 수 있었던 3,032개를 대조했다. 615개는 두 선형의 최대 이격 거리(Hausdorff 거리)가 1m를 넘었고, 그중 414개는 5m를 넘었다. 선형이 이동한 경우와 길이·분할 범위가 달라진 경우가 함께 들어 있는 값이다. 오래된 원본의 차선을 옮겨 맞추기 전에 최신 도형을 확인해야 하는 이유다.

2023년 시설물 현황의 대표 좌표 356,711개를 2021년 기본 차선과 2026년 버스전용차로를 병합한 선형에 대조했다. 가장 가까운 선에서 1cm 이내인 좌표는 302,768개였고, 5m 안에 선이 하나도 없는 좌표는 7,402개였다. 후자는 25개 구 모두에서 나왔다. 차선 종류와 관리번호를 묶은 비교가 아니므로 이 차이만으로 신규·이설·삭제를 구분할 수 없다. 대표 좌표는 최신 선형이 필요한 위치의 후보로 활용한다.

## 서울 전체 1차 대조

길이가 25cm보다 긴 유효 선형이 있는 차선 기록 339,953건을 최대 2m 간격으로 표본화했다. 표본이 차도와 보도 폴리곤 중 어디에 걸치는지 비교한 결과다. 조사한 15,723.1km는 평행 차선 표시를 각각 센 길이이므로 도로 연장을 뜻하지 않는다.

| 표본 위치 | 조사 길이 기준 비율 |
| --- | ---: |
| 차도 면에만 포함 | 88.4% |
| 차도와 보도 면에 모두 포함 | 3.8% |
| 보도 면에만 포함 | 약 0.01% |
| 두 면 밖이지만 차도에서 0.5m 이내 | 2.3% |
| 나머지 차도 밖 | 5.4% |

차도에만 포함되는 비율은 구별로 81.2~92.4%였다. 도로 층위나 방향을 가리지 않은 평면 검사여서, 교량 위 차선이 아래 차도와 겹치는 경우도 있을 수 있다. 누락 원인과 현재 차선 상태는 도로 구간별 연결과 최신 원본으로 검증한다. 기존 공개 장면의 렌더러 탈락 집계는 도로 생성·횡단 표시 절단까지 적용한 별도 지표다. [공개 장면 기준선](road-markings.md#공개-장면-전수-점검)

## 서울 전체 도로면 연결 결과

25개 구의 2021년 기본 차선과 2026년의 유효한 버스전용차로 도형을 하나의 공간 인덱스에 넣었다. 최신 버스전용차로 관리번호 3,247개 가운데 기본 차선과 일치한 3,032개를 교체하고 최신 도형의 출처를 기록했다. 인덱스에는 도로면 311,290건, 보도면 60,715건, 차선 도형 340,162개와 위치별 연결 구간 806,797개가 들어 있다.

이 단계는 원본 선형과 도로면·보도면이 실제로 만나는 위치에서 구간을 나눈다. 원래 선의 좌표와 관리번호를 유지하고 각 구간에 시작·끝 거리, 겹치는 도로면 후보, 해당 후보의 UFID를 기록한다. 단순 평면 표본 조사와 달리 연결 구간 길이를 직접 합산할 수 있다.

| 연결 상태 | 차선 길이 |
| --- | ---: |
| 보도와 겹치지 않고 도로면 하나에만 포함 | 13,633.5km (86.6%) |
| 도로면 여러 개와 겹침 | 278.2km |
| 도로면과 보도면에 모두 포함 | 599.9km |
| 보도면에만 포함 | 1.3km |
| 도로·보도면 밖 | 1,221.3km |

가락과 강서에서 원본을 다시 내려받지 않고 각각 필요한 범위의 GeoJSON을 뽑았다. 차도·보도 형상과 차선 상태를 함께 내보내 가락에서 719개, 강서에서 1,795개의 차선 조각을 검토할 수 있었다. 도로면 하나와 겹친 기록에도 방향과 높이 판단이 남아 있다. 여러 후보가 있는 곳의 차선과 원본 도형도 인덱스에 보존해 정밀도로지도와 최신 서울시 원본이 들어오면 같은 위치를 다시 대조할 수 있다.

### 가락 정문처럼 도로면이 빠진 곳

지금까지 문제가 반복된 가락 정문 황색 실선 `11-0000104759`의 30.81m 전부가 서울시 일반 도로면 범위 밖이었다. 부지안도로 원본의 양쪽 경계를 자동으로 대조하자 일곱 단면 모두에서 UFID 끝자리 216과 151인 선이 이어졌다. 두 선 사이의 간격은 약 14.9~16.1m였다. 주변 경계선을 폐합하면 이 실선을 포함하는 면이 나오지 않아, 실제 차량 포장 폭과 양끝 접속은 추가 근거로 확인해야 한다. [서울시 부지안도로 원본](https://openlab.eseoul.go.kr/qgisplugin/SHP/N1L_A0010000.zip) · [가락 정문에서 확인한 원인](road-markings.md#가락-정문에서-확인한-원인)

같은 검사를 서울 전체의 3m 이상 도로면 밖 구간 38,561개에 적용했다. 정지선을 제외하고 최대 5m 간격으로 단면을 만들었으며, 양옆 18m 안에서 동일한 원본 경계 한 쌍이 계속 확인되는 경우만 후보로 집계했다. 검사한 약 1,191km 가운데 1,156개 구간, 약 22.8km(1.9%)에서 양쪽 경계 후보를 찾았다. 후보마다 차선 관리번호와 양쪽 경계 UFID를 기록했다. 포장과 접속부가 확인되면 해당 구간을 다시 검증하고, 다른 구간은 최신 차도면과 층위 자료로 보강한다.

### 서울 전역 실폭도로 대조

브이월드에는 행정안전부의 `(도로명주소)실폭도로_서울.zip`이 서울 전체 한 파일로 올라와 있다. 2026-11 상태로 표시된 자료의 갱신일은 2026-11-13, 표시 용량은 26MB, 카탈로그 좌표계는 EPSG:5179다. 원본 다운로드에는 로그인이 필요하며 브이월드 자료 담당자는 이 레이어의 API를 제공하지 않는다고 안내한다. [실폭도로 다운로드와 데이터 문의](https://www.vworld.kr/dtmk/dtmk_ntads_s002.do?svcCde=MK&dsId=30057) · [행정안전부 도로명주소 전자지도](https://www.data.go.kr/data/15050413/fileData.do)

이 자료를 확보하면 동일한 좌표계로 변환해 기존 차도·보도 둘 다 밖에 있는 차선 구간 60,713개, 약 1,221.3km를 한 번에 검사할 수 있다. 겹친 길이는 실폭도로 폴리곤 하나에 포함된 부분, 여러 폴리곤에 겹친 부분, 여전히 도로 밖인 부분으로 나눠 기록한다. 차선 관리번호에 연결되는 구간 키와 실폭도로의 파일명·레코드 번호를 보존한다. 기존 서울시 차도면을 대조군으로 입력했을 때 25개 구의 전체 길이와 가락 정문의 도로면 밖 30.81m가 그대로 재현됐다. [실폭도로 비교 코드](../../backend/scripts/compare_seoul_road_surface.py)

서울 25개 구를 대상으로 한 연구에서 2025년 10월 실폭도로의 도로 경계 꺾임점 3,768개를 항공 정사영상과 대조했을 때 평균 거리 오차는 1.87m였다. 따라서 이 레이어와 겹친다는 사실은 포장 후보의 근거로 사용한다. 차선 위치와 도로 층위는 최신 노면표시 선형과 구조물 자료로 각각 확인한 뒤 연결한다. 가락 정문을 포함한 실제 2026년 실폭도로의 수록 여부는 ZIP을 받아 검사해야 한다. [도로명주소 실폭도로 위치오차 연구](https://www.ksgpc.or.kr/jksgpc/journal/thesisPrint/Vol/1554.pdf)

## 서울 전체 도로중심선·입체도로 검사

위 인덱스의 806,797개 구간을 서울시 에스맵 도로중심선과 대조했다. 차선이 도로면 하나와 겹치는 부분을 최대 4m 간격으로 검사했다. 16m 안에서 같은 도로면 위의 중심선을 찾고, 진행 축과 25° 이내로 나란한지 확인했다. 정지선은 중심선과 직각에 가까운지 봤다. 서로 다른 중심선의 거리 차가 1m 이내면 여러 후보로 남겼다. 원본 차선 좌표, 중심선 UFID와 분류별 길이를 저장했다.

| 표본별 판정 | 차선 길이 | 전체 차선 길이 기준 |
| --- | ---: | ---: |
| 같은 도로면에서 방향이 맞는 중심선 후보 하나 | 11,619.0km | 73.8% |
| 중심선 후보 여러 개 | 1,170.0km | 7.4% |
| 같은 도로면에서 조건에 맞는 중심선 없음 | 844.5km | 5.4% |
| 도로면을 하나로 특정하지 못함 | 2,100.7km | 13.4% |

첫 항목은 구별로 64.8~80.3%였다. 한 구간 안에서도 위치마다 다른 중심선이 후보가 될 수 있다. 이 비율은 기존 차선 도형이 도로면과 진행 축에 맞는 정도를 보여준다. 차선 설치 시점, 차량 통행 방향, 동일한 구조물 위에 있는지는 별도 근거로 확인한다.

일반도로의 표준노드링크와 입체도로의 링크가 둘 다 16m 안에 있는 표본은 전체 차선 길이 중 981.8km(6.2%)였고, 25개 구 모두에서 찾았다. 가락 정문의 30.81m는 전체가 도로면 미확정으로 유지됐다. 검수에서 구조가 가까이 잡히면 해당 링크 ID와 구조 종류를 남기고, 배포 전에 어느 차도에 붙이는지 별도 도형으로 확인한다. 링크 검색은 평면 거리 기준이므로 구조 링크가 보이지 않는 곳도 실제 높이는 추가 자료로 확인한다. 링크가 표현하는 교통망을 차선 좌표나 도로 높이로 변환하지 않는다. [국가교통정보센터 표준노드링크 자료실](https://www.its.go.kr/nodelink/nodelinkRef) · [국토교통부 표준 노드·링크 구축기준](https://www.law.go.kr/LSW/admRulLsInfoP.do?admRulId=32722&efYd=0)

## 국토지리정보원 정밀도로지도 일괄 확보 경로

2026-11-22에 국토정보플랫폼의 공개 벡터 목록과 구축현황을 대조했다. 벡터 목록에 서울 25개 구의 항목이 모두 있고, 로그인 후 여러 항목을 골라 **선택다운로드**를 실행하는 경로가 있다. 구축현황에서 구 이름으로 확인되는 항목은 모두 **2023년 구축**으로 표시됐으며 25개 구에 서로 다른 구간 ID가 **464개** 있었다. 2026년의 동작·서울생활권·청계천 자율주행 시범운행지구는 별도 항목으로 조회된다. [정밀도로지도 벡터 목록](https://map.ngii.go.kr/ms/pblictn/preciseRoadMap.do) · [국토정보맵 구축현황](https://map.ngii.go.kr/ms/map/NlipMap.do)

송파구 39개 구간에는 송이로와 중대로1·2길이 있다. 가락 정문 주소의 송파대로32길은 구간 이름 목록에서 확인되지 않았다. 구간 이름은 여러 도로를 묶기도 하며, 464개 구간의 거리 항목은 0으로 반환되어 목록에서 도로 길이 비율을 계산할 수 없었다. 파일 선택 화면의 ID와 구축현황의 연도도 따로 기록했다. 실제 SHP의 수록 경계, 측량일과 노면표시의 높이까지는 로그인 후 받은 파일에서 확인한다.

1. [국토정보플랫폼 벡터 목록](https://map.ngii.go.kr/ms/pblictn/preciseRoadMap.do)에서 로그인하고 서울 25개 구를 선택한다. 최신 구축현황에서 별도로 확인되는 도로는 [국토정보맵 정밀도로지도](https://map.ngii.go.kr/ms/map/NlipMap.do)에서 구축연도와 구간을 찾아 함께 받는다.
2. 받은 묶음에서 노면선표시와 도로 연결 도형을 읽고, 실제 포함 범위·측량일·좌표계·높이 기준을 확인한다. 앞의 서울시 차선 인덱스와 대조해 범위 안에서 증거가 있는 도형을 갱신한다. 권역에 걸친 도로는 원본 구간 ID를 따라 중복을 제거한다. [정밀도로지도 제공 항목과 공공누리 조건](https://www.data.go.kr/data/15059912/fileData.do)
3. 정밀도로지도에서 실제 도형이 빠진 도로는 서울시 전체 T-GIS 최신 선형과 차도면으로 보강한다. 가락 정문처럼 기존 차도면에서 빠진 곳은 정밀도로지도 원본에서 포장 도형을 확인한다. 여기서도 빠진 곳은 별도로 표시하고 최신 차도면에 공동주택 부지 도로까지 포함되는지 확인한다.

## 수작업을 줄이는 생성 방식

1. **도시 단위 스냅샷을 먼저 만든다.** 위 파일을 한 캐시에 받고 버전·해시를 기록한다. 보도, 차도, 횡단보도, 중심선, 차선을 도시 공통의 공간 인덱스에 넣고, 배포할 때만 같은 범위의 타일로 자른다. 같은 도로가 여러 단지에 걸려도 한 번 연결한다.
2. **차선을 실제 차도에 연결한 뒤 3D를 만든다.** 차도 폴리곤과 중심선의 관계를 먼저 만들고 도로 구간, 방향, 층위, 차도 경계를 저장한다. 실선 등 길이 방향 표시는 연속으로 겹치는 길이·방향·옆 차도와의 분리 여부로 연결한다. 정지선과 횡단보도는 교차로·진입로의 가로 방향과 경계를 대조한다. 원본의 차선 선형을 보존하고, 접속부의 차도 면만 동일한 근거의 경계에 맞춘다. 다른 층에 겹치거나 후보 도로가 여럿이면 미확정으로 남긴다.
3. **원본 관리번호는 갱신에 쓴다.** 2021년 유효 차선 모두에 `MGRNU`가 있고 `SIXID`는 200,496건에 있다. 도로명 코드 `RN_CDE`는 이 파일의 유효 레코드에서 비어 있다. 관리번호가 같은 최신 레코드는 병합 후보로 사용하고, 한 번호에 여러 조각이 있으면 도형과 범위를 함께 비교한다. 도로 면은 별도 `UFID`를 가지므로 차선 식별자만으로 도로에 연결할 수 없다.
4. **최신 원본과 공개 범위를 분리해서 관리한다.** 서울 25개 구 전체의 최신 T-GIS 선형을 구할 때는 시 전체 스냅샷을 한 번에 요청한다. 제공 항목은 관리번호, 유형, 도로 구간 및 층위 연결자, 조사·갱신 기준일, 수집 범위와 공개 웹서비스 가공·제공 조건이다. 국토지리정보원 정밀도로지도의 구별 묶음과 최신 노선은 실제 포함 구간에 쓴다. 서울시 자체 시범사업의 공식 발표 범위는 상암 약 20km다. [서울시 공공데이터 제공신청](https://data.seoul.go.kr/etc/offerReqst.do) · [국토지리정보원 공개 구축현황](https://map.ngii.go.kr/ms/map/NlipMap.do) · [서울시 정밀도로지도 시범 자료](https://itskorea.kr/downloadFile.do?fileId=FILE_000000000102013&fileSn=0)
5. **자동 검수 후 근거가 있는 구간을 배포한다.** 출처가 확인된 차선, 원본에서 차선 없음이 확인된 도로, 미수집·불일치 도로를 각각 기록한다. 차선이 잘렸거나 보도·다른 층으로 간 위치를 목록으로 남겨 최신 자료와 대조한다. 공개 타일의 차도와 도색은 같은 구간 연결 결과에서 생성한다. [상세 배포 기준](road-markings.md#배포-전-점검-기준)

서울시에 전달할 요청 내용 예시

> 서울 25개 구의 T-GIS 차선·정지선(`A058_L`)과 횡단보도·노면표시 전체 선형 최신 원본을 GeoPackage 또는 SHP로 받을 수 있는지 확인 요청드립니다. 공개된 2021년 선형에는 이후 변경 내용을 확인하기 어렵습니다. 관리번호, 분류코드, 도로·교차로 연결키, 방향·층위, 설치·변경일, 삭제 이력 또는 변경분, 측량 범위와 좌표계가 필요합니다. 자료는 실제 도로와 보행환경을 보여주는 온라인 3D 임장에 사용합니다. 웹 타일로 가공해 공개 서비스로 제공할 때의 이용 조건도 함께 안내 부탁드립니다.

## 공개 장면 일괄 갱신

서울 10개 장면의 차선 23,950개를 기존 기준 범위와 2021년 원본으로 재현했다. 이어 서울 전체 인덱스에서 2026년 버스전용차로를 반영한 차선을 읽고 같은 범위로 잘랐다. 이렇게 10개 장면에 **관리번호 191개, 장면별 중복을 포함해 252개 선형 조각**을 연결했다. 횡단보도, 감속 표시, 보도 자료는 이번 갱신의 비교 기준으로 사용했다. 2026년 버스전용차로 ZIP 공개일은 2월 13일이고 ZIP 안의 SHP 색인 파일 날짜는 2월 12일이다. 장면별 JSON에 ZIP 해시, 적용한 출처와 범위, 갱신 선형의 관리번호를 기록했다. [서울시 버스전용차로 위치](https://data.seoul.go.kr/dataList/OA-22396/F/1/datasetView.do)

청색 실선·점선·복선은 서울시 차선 유형 코드로 구분한다. 점선의 도색과 빈 간격은 경찰청 규격을 따라 3m씩 모델링했다. 겹치는 장면에서 점선이 다른 위치로 옮겨 보이는 일을 줄이기 위해, 잘린 첫 좌표가 원본 선의 시작점에서 얼마나 떨어져 있는지도 전달한다. 두 줄로 된 점선은 같은 시작 위치에서 나눈다. 원본에는 개별 도색 조각의 길이·시작점이 따로 들어 있지 않다. [서울시 차선 정의서](https://data.seoul.go.kr/dataList/OA-15537/S/1/datasetView.do) · [경찰청 교통노면표시 업무편람](https://itskorea.kr/downloadFile.do?fileId=FILE_000000000038775&fileSn=2)

## 재현 명령

Python 3.11 이상에서 실행한다. 작업 폴더의 `road-source-cache`에는 원본을 저장하고, 결과 JSON에는 자치구별 거리 합계, 도형 개수, CRS, 파일 해시와 번호 일치 건수를 남긴다. 기본 실행은 캐시만 사용하고 `--download`를 붙이면 누락된 원본도 받는다.

```powershell
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/audit_seoul_road_sources.py ../road-source-cache --download --output ../road-source-cache/coverage.json
```

[일괄 수집·평면 대조 코드](../../backend/scripts/audit_seoul_road_sources.py)

도시 단위 인덱스를 만든 뒤에는 원하는 범위만 반복해서 내보낼 수 있다. 각 GeoJSON의 차선 조각에는 원본 종류, 관리번호, 위치 판정과 단일 후보인 경우 차도 UFID가 포함된다. `--bbox`는 서·남·동·북 순서의 WGS84 경도·위도다.

```powershell
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/index_seoul_road_markings.py ../road-source-cache ../road-source-cache/seoul-marking-index.sqlite --latest-bus
uv run --with pyshp --with shapely --with pyproj python backend/scripts/extract_seoul_road_window.py ../road-source-cache/seoul-marking-index.sqlite ../road-source-cache/garak-markings.geojson --bbox 127.1125 37.4965 127.1195 37.5005
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/probe_seoul_internal_road_edges.py ../road-source-cache ../road-source-cache/seoul-marking-index.sqlite ../road-source-cache/internal-edge-candidates.json
```

[도시 인덱스 생성](../../backend/scripts/index_seoul_road_markings.py) · [생활권 추출](../../backend/scripts/extract_seoul_road_window.py) · [부지안도로 경계 후보 검사](../../backend/scripts/probe_seoul_internal_road_edges.py)

위 인덱스의 선형으로 공개 장면을 갱신한다. `--output`을 지정하면 다른 디렉터리에 생성해 전후를 비교할 수 있다.

```powershell
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/prepare_seoul_lane_windows.py ../road-source-cache ../road-source-cache/seoul-marking-index.sqlite
```

국가교통정보센터에서 [2026-11-11 전국 ZIP](https://www.its.go.kr/opendata/nodelinkFileSDownload/DF_222/0)을 `national-road-links-2026-11-11.zip`으로 저장한 뒤 실행한다. 다음 스냅샷도 ZIP 하나를 교체해 전체를 다시 검사한다. SQLite의 `evidence`는 차선 인덱스의 구간과 같은 키를 사용한다. 구별 합계와 입력 해시는 `metadata`의 `report`와 표준 출력에서 확인한다.

```powershell
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/reconcile_seoul_marking_links.py ../road-source-cache ../road-source-cache/seoul-marking-index.sqlite ../road-source-cache/national-road-links-2026-11-11.zip ../road-source-cache/seoul-marking-link-evidence.sqlite
```

[도로중심선·입체도로 대조 코드](../../backend/scripts/reconcile_seoul_marking_links.py)

서울 실폭도로 ZIP을 내려받은 뒤 아래처럼 저장 경로를 지정해 비교한다. 출력 SQLite의 `surface_check`는 원래 인덱스와 같은 차선 구간 키를 쓰며 `--marking-id`는 가락 정문처럼 특정 관리번호를 결과 요약에 포함한다.

```powershell
uv run --with pyshp --with shapely --with pyproj --with openpyxl python backend/scripts/compare_seoul_road_surface.py ../road-source-cache/seoul-marking-index.sqlite ../road-source-cache/vworld-seoul-road-width.zip ../road-source-cache/seoul-road-width-check.sqlite --marking-id 11-0000104759
```
